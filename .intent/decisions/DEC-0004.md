## Context

Services need to call each other (e.g. marketplace notifies notifications-service). These calls must be authenticated to prevent spoofing, but a full JWT flow would be circular and slow.

## Decision

All service-to-service HTTP calls include the `x-internal-key` header set to `INTERNAL_API_KEY`. Receiving services validate this key in their internal route middleware. The key is shared across all services via `env/.env.shared`.

Calls use Docker network hostnames (e.g. `http://notifications-service:4016`). The `INTERNAL_API_KEY` is the only credential needed on the internal network.

## Consequences

- Simple and fast — no JWT verification overhead for internal calls.
- `INTERNAL_API_KEY` must be a strong secret (`openssl rand -hex 32`) and must never be exposed externally.
- Internal routes (e.g. `/internal/notify`, `/internal/push`, `/internal/wishlist-match`) must be protected by the internal key guard middleware.
- If the Docker network is compromised, the internal key is the only barrier.
