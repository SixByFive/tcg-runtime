## Context

Collection/wishlist/binder entries in collections-service store only `cardId` + user metadata (quantity, condition, etc.). Clients need full card data (name, images, prices, set). Two options:

1. Collections-service calls catalog-service to enrich entries before returning them.
2. Gateway resolvers call catalog-service to enrich entries after receiving them from collections-service.

## Decision

Hydration happens **in the gateway** via `hydrateCards()` (`apps/gateway/src/graphql/resolvers.js`). The resolver:

1. Calls collections-service to get the raw entries (cardId + metadata).
2. Extracts all unique `cardId` values.
3. Batch-fetches full card data from catalog-service's `/internal/cards/batch`.
4. Merges card data onto each entry.
5. Falls back gracefully (returns entries with minimal data) if catalog is unreachable.

## Consequences

- Collections-service stays simple — no knowledge of card shapes.
- Catalog-service is a pure data store — no user context needed.
- The gateway is the composition layer. Adding a new hydrated field means updating `hydrateCards` and the gateway schema.
- Never add card-detail columns (`name`, `images`, `prices`) to `user_collections`, `wishlist_items`, or `binder_cards` tables.
