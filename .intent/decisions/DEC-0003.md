## Context

Web clients use HttpOnly cookies (`sbf_access`, `sbf_refresh`) for token storage — this is the most secure option for browsers. Mobile apps cannot use HttpOnly cookies in the same way; they store tokens in secure storage (e.g. `expo-secure-store`) and attach them as `Authorization: Bearer` headers.

## Decision

Auth-service detects `X-Client-Type: mobile` in the request header. When present:
- `login` and `register` return `{ token, user }` in the JSON response body instead of setting cookies.
- The mobile app stores the token in `expo-secure-store`.

The gateway's auth middleware accepts **either** the `sbf_access` cookie **or** an `Authorization: Bearer <token>` header.

## Consequences

- Web and mobile share the same auth endpoints — no separate mobile endpoints needed.
- Mobile token storage and transmission is the app's responsibility (`lib/apollo.js` auth link).
- Token rotation for mobile: the mobile app must handle 401 responses and re-authenticate (no silent refresh like cookie-based web).
